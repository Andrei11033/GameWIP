# GameWIP Decisions

## Purpose

This file records stable project decisions for GameWIP.

A decision belongs here when it affects the long-term direction, architecture, coding standards, tooling, documentation, or library contracts of the project.

This file is not a task checklist and not a proof checklist.

* Use `roadmap.txt` for ordered future work.
* Use `implementation_checklist.txt` for what has been implemented.
* Use `testing_checklist.txt` for what must be proven by tests.
* Use dedicated contract files for detailed backend or library contracts when a section becomes too large.

---

# 1. Project Direction

## Tech Stack

GameWIP currently targets:

* Language: C++23
* Compiler: g++ through MSYS2 UCRT64
* Build system: CMake
* Build tool: Ninja
* Editor: Visual Studio Code
* Version control: Git
* First platform target: Windows

Linux and other platforms may be added later, but Windows is the v1 target.

## Development Priorities

The project is developed simulation-first.

Current priority order:

1. physics core;
2. simulation foundation;
3. destructible structural world;
4. component damage model;
5. component framework;
6. simple components;
7. logic and control;
8. advanced systems;
9. gameplay;
10. multiplayer later.

Graphics are important, but they should support simulation development first instead of becoming the first major project focus.

# 2. Rendering and Simulation Decisions

## Rendering

Early rendering should be minimal and debug-focused.

The first rendering goal is not visual polish. It is to make simulation, physics, structures, damage, and debugging easier to inspect.

Early rendering should support:

* opening a window;
* drawing simple objects;
* debug drawing;
* transforms;
* camera movement;
* on-screen debug information.

A full graphics engine is not the first priority.

## Simulation

Simulation must use a fixed timestep.

Rendering and simulation updates must be separate. The simulation should behave consistently at different render frame rates.

Only selected systems should run at high frequency. High-rate updates are reserved for systems that need them, such as:

* stabilizers;
* servos;
* missile guidance;
* sensors;
* weapons;
* control loops.

Normal gameplay systems should not automatically run at the highest simulation rate.

# 3. Building, World, and Component Decisions

## Building

Base building should be simple and approachable.

The basic building experience should feel close in spirit to Stormworks: fast to use, easy to understand, and not overloaded with mandatory engineering details.

Advanced configuration should exist only where it adds meaningful depth.

## Structural World

Vehicles and buildings should share the same structural backbone where possible.

The world and map direction should be closer to Space Engineers in scale and structure, while supporting more granular damage behavior.

Placed parts may appear large to the player, but they may still be internally subdivided for damage, connectivity, and destruction.

## Destruction

Structural destruction should be granular.

Damage should affect:

* cell health;
* structural strength;
* connectivity;
* detached regions;
* component exposure;
* component degradation;
* component detachment;
* vehicle behavior.

Destruction should not be only visual.

## Components

Components must support meaningful damage states.

At minimum, component behavior should allow:

* healthy state;
* degraded state;
* damaged state;
* detached state;
* destroyed or non-functional state.

Simple default components must always exist.

Advanced editing should be available only for selected systems where extra configuration is useful. The project should avoid making every component complicated by default.

# 4. Foundation Library Standards

The Logger, Assert, and TestSupport libraries are foundation code.

They should be treated as reusable libraries, not temporary game helpers.

A foundation library feature is complete only when:

* its public contract is documented;
* normal paths are tested;
* failure paths are tested where practical;
* hot-path performance is understood.

## Foundation Dependency Direction

Foundation and tool dependencies follow this direction:

```text
Logger -> Terminal + FileSystem + IO
Assert -> Logger
TestSupport -> standard library + its own platform backend
```

IO and FileSystem remain static libraries because their runtime state belongs to caller-owned objects. Terminal is a shared library because standard streams, stream serialization, input modes, cursor scopes, and alternate-screen nesting are process-wide. Logger and the enabled Assert runtime remain shared libraries so their process state is not duplicated across modules.

TestSupport is the standalone exception. It must not depend on any project library.

# 5. Logger Decisions

## Logger Contract

Normal log calls are asynchronous, queue-based, and filterable.

Normal log calls include:

* `trace`;
* `debug`;
* `info`;
* `warn`;
* `error`;
* `fatal`.

`Logger::fatal(...)` is a fatal-severity log message. It does not automatically force a popup, synchronous flush, or process termination.

`Logger::report(...)` is the synchronous diagnostic path.

Reports must:

* bypass level filters;
* bypass source filters;
* bypass the async queue;
* write immediately to active sinks;
* mirror to platform debug output when enabled;
* flush sinks;
* never terminate the process by themselves.

`Logger::report(timeout)` writes the report first, then attempts a bounded queue/sink drain. A timeout means the bounded drain failed, not that the report line was lost.

`reportError`, `reportFatal`, and `fatalTerminate` are convenience APIs over the report path. `reportFatal` and `fatalTerminate` may use the logger-owned fatal popup when configured.

## Logger Counters

Queue-drop counters represent queue pressure only.

Filtered messages are intentional skips and must not count as drops.

Unknown `SourceId` values are accepted, written with fallback source text, and counted through `unknownSourceUses`.

## Logger Public Shape

`GameWIP::Logger` is a namespace-style module API, not a static-only class.

Logger is process-wide and currently exposes module functions such as `init`, `shutdown`, `info`, `report`, and `flush` directly under `GameWIP::Logger`.

Logger passive public data stays under `GameWIP::Logger::Types`.

This keeps Logger consistent with other library-style APIs and allows internal code to use the standard `Detail` namespace layout.

# 6. Assert Decisions

## Assert Contract

Fatal assertion paths:

* `ASSERT`;
* `VERIFY`;
* `UNREACHABLE`.

Recoverable diagnostic paths:

* `CHECK`;
* `CHECK_ONCE`;
* `ENSURE`.

`ASSERT_INTERACTIVE` and `VERIFY_INTERACTIVE` are separate developer/debug features. They do not change the behavior of normal `ASSERT` or `VERIFY`.

Interactive assertion actions are:

* `Break`;
* `Abort`;
* `IgnoreOnce`;
* `AlwaysIgnore`.

`AlwaysIgnore` is local to the macro call site.

Automated interactive tests must use `INTERNAL_ASSERT_TEST_ACTION` and must not open real popups.

Manual UI tests are separate. They may show real Windows UI, may block, and should run near the end of the test run.

# 7. TestSupport Decisions

`tools/test_support` is the shared test support library.

It is used by logger tests, assert tests, and future engine tests.

## Public Identity

* Target: `TestSupport`
* Namespace: `GameWIP::TestSupport`
* Public header: `tools/test_support/test_support.h`
* Library type: static library

## Dependency Rule

TestSupport must not depend on any other project library, including IO, FileSystem, Terminal, Logger, Assert, engine, or game code.

Logger, Assert, foundation, engine, and game tests may depend on TestSupport, but TestSupport must not know about their concepts.

## Purpose

TestSupport is not a replacement for GoogleTest.

It is a small project-native support layer for:

* reports;
* expectations;
* child processes;
* manual checks;
* diagnostic elapsed timing;
* files;
* environment variables;
* stress helpers.

## Runtime Test Control

Runtime test behavior belongs in runtime options, not in CMake test-selection options.

CMake controls compile-time and build features.

Runtime options control things such as:

* stress tests;
* automated interactive tests;
* manual UI tests;
* logger popup tests;
* child crash tests;
* thread counts;
* report output paths.

Benchmark iteration, timing, repetition, and statistics belong to Google Benchmark, not TestSupport runtime options.

# 8. Public API Organization

## Namespace and Type Layout

Passive public data shapes live under:

```cpp
GameWIP::<Library>::Types
```

Passive data shapes include:

* configs;
* options;
* results;
* summaries;
* enums;
* simple value structs;
* wrapper values whose main purpose is to carry data across API calls.

Active behavior stays directly under:

```cpp
GameWIP::<Library>
```

Active APIs include:

* functions;
* runners;
* contexts;
* RAII guards;
* timers;
* synchronization helpers;
* services;
* objects whose purpose is to perform work or manage lifetime.

## Aliases

Do not add top-level aliases for `Types` members unless compatibility with already-shipped API requires it.

Keeping passive data under `Types` makes IntelliSense and documentation easier to scan.

## Internal Namespace Layout

Internal implementation namespaces stay under the owning library namespace.

Use this standard layout for reusable foundation and tool libraries:

```cpp
GameWIP::<Library>::Detail
GameWIP::<Library>::Detail::Core
GameWIP::<Library>::Detail::Platform
GameWIP::<Library>::Detail::TestHooks
GameWIP::<Library>::TestHooks
```

Meaning:

* `GameWIP::<Library>` is the public production API.
* `GameWIP::<Library>::Types` contains passive public data shapes.
* `GameWIP::<Library>::TestHooks` contains callable test-only hook APIs, gated by the matching compile-time test-hook flag and declared only in internal headers.
* `GameWIP::<Library>::Detail` contains implementation details.
* `Detail::Core` contains platform-neutral internal implementation details.
* `Detail::Platform` contains internal platform backend declarations/definitions.
* `Detail::TestHooks` contains private hook state and hook machinery used by backend/core code.

Do not create sibling detail namespaces such as:

```cpp
GameWIP::LoggerDetail
GameWIP::TerminalDetail
```

Namespaces do not make code private by themselves. Privacy comes from public headers not including internal headers, internal headers not being installed as public API, compile-time hook gates, and documentation marking `Detail`/test-hook internals as non-production API.

Future modernization may revisit this for reusable foundation and tool libraries with C++ modules and exported module interfaces. In that model, public headers may become compatibility wrappers that import module interfaces, public API names would be explicitly exported, and non-exported implementation code could keep `GameWIP::<Library>::Detail` without exposing it to importers. Assert may remain header/macro-based longer than the other libraries because assertion macros must expand to names visible from the consuming translation unit.

# 9. Naming Standard

Public C++ types use `PascalCase`.

Public C++ functions use `camelCase`.

Private/internal helpers use `camelCase`.

Private/internal structs and classes use `PascalCase`.

Constants use `kPascalCase`.

Macros use `UPPER_SNAKE`.

GameWIP-owned configuration macros use the `GAMEWIP_` prefix.

CMake project-level options use:

```text
GAMEWIP_BUILD_...
GAMEWIP_ENABLE_...
GAMEWIP_RUN_...
```

CMake library-local options use library-specific prefixes such as:

```text
LOGGER_...
ASSERT_...
TEST_SUPPORT_...
```

Internal compiler macros use ownership after the `INTERNAL_` prefix:

```text
INTERNAL_LOGGER_...
INTERNAL_ASSERT_...
INTERNAL_TERMINAL_...
INTERNAL_TEST_SUPPORT_...
```

Names should describe the current contract, not stale implementation history.

Avoid global namespace pollution.

Test hooks live only under internal namespaces when enabled.

# 10. Platform Backend Standard

Tool libraries keep public headers and core implementations platform-neutral.

Operating-system-specific behavior lives behind internal platform headers and platform source files.

Platform files use this structure:

```text
platform/<platform-id>/
```

The current Windows platform id is:

```text
win32
```

`cmake/LibraryPlatform.cmake` resolves `LIBRARY_PLATFORM_ID`.

Library CMake files consume platform files by convention:

```text
platform/${LIBRARY_PLATFORM_ID}/*.cpp
```

A backend folder may also include:

```text
platform/${LIBRARY_PLATFORM_ID}/platform.cmake
```

Use `platform.cmake` only for platform-local needs, such as:

* system libraries;
* compile definitions;
* resources;
* manifests;
* generated files.

Adding a new platform should normally require adding a matching backend folder, not editing core implementation files.

# 11. Windows Unicode Standard

Windows platform code uses explicit Unicode Win32 APIs.

Public library C++ APIs stay portable and ergonomic:

* text uses UTF-8 `std::string`;
* paths use `std::filesystem::path`.

At the Win32 boundary, platform backends convert to UTF-16 and call explicit `W` APIs.

Use explicit APIs such as:

```cpp
CreateProcessW
MessageBoxW
GetEnvironmentStringsW
SetEnvironmentVariableW
OutputDebugStringW
```

Do not use ANSI APIs such as:

```cpp
CreateProcessA
MessageBoxA
GetEnvironmentStringsA
OutputDebugStringA
```

Also avoid generic macro-mapped APIs such as:

```cpp
CreateProcess
MessageBox
GetEnvironmentStrings
OutputDebugString
```

Their behavior depends on the `UNICODE` build definition and can silently change between ANSI and Unicode variants.

Captured child-process output remains byte-oriented `std::string`, because stdout and stderr pipes carry bytes.

This standard applies to Logger, Assert, TestSupport, and future Windows backends.

# 12. Documentation and IntelliSense Standard

Public API comments use professional Doxygen-style documentation focused on contracts.

Public headers should explain:

* behavior;
* lifecycle expectations;
* thread-safety;
* failure behavior;
* blocking or UI behavior;
* important performance notes.

Detailed tutorials, complete usage explanations, examples, and edge-case discussions belong in generated Doxygen Markdown manual pages, not in hover-heavy header comments.

Documentation ownership follows code ownership. A library manual explains only that library's public API, behavior, examples, troubleshooting, and library-specific validation surface. Root project pages explain GameWIP integration, build presets, startup sequencing, modular validation, report placement, CI, and repository policy. Cross-boundary pages link to the authoritative owner instead of duplicating a contract.

## Public Header Style

Public headers should:

* start with `/// @file`;
* include `/// @brief`;
* document public namespaces, types, enum values, fields, functions, macros, and important templates;
* use `@param`, `@return`, and `@note` where useful;
* keep the first line short and useful for IntelliSense;
* avoid long examples or tutorials in hover text.

Use plain sections such as:

```text
Contract:
Thread-safety:
Failure behavior:
Blocking behavior:
Performance:
```

Implementation helpers may use `@cond` / `@endcond` when they must appear in a public header but should not be treated as normal public API.

## Internal Source Style

Internal headers and implementation files are maintainer documentation. Every named internal namespace, type, function, and non-obvious constant should have a concise purpose comment at its declaration or definition.

Internal comments should add the contract that cannot be recovered safely from the signature alone, including:

* ownership and lifetime;
* lock and atomic ordering;
* state transitions and shutdown invariants;
* platform-boundary behavior;
* fallback and failure-injection behavior;
* units, limits, and hot-path constraints.

Do not narrate assignments, loops, obvious accessors, or self-explanatory local variables. Local lambdas need comments only when they encode a non-obvious invariant or protocol. Internal comments are source-maintenance guidance and are not added to the generated public Doxygen input set.

## Markdown Manual Pages

The generated Doxygen manual must cover every public API.

Simple APIs may be fully covered by header reference.

Non-trivial APIs should also have Markdown guide pages covering:

* usage rules;
* edge cases;
* examples;
* performance notes;
* troubleshooting;
* common patterns.

The manual must account for every public namespace, type, enum value, field, function, macro, and public constant. Closely related overloads or enum values may be explained together in a table when their behavior is genuinely shared. Reference pages should state defaults, units, ownership, thread-safety, blocking behavior, failure behavior, side effects, and compile-time availability wherever those properties apply.

Each reusable library may own a `docs/` folder beside its source.

Examples:

```text
tools/logger/docs/
tools/debug/assert/docs/
tools/test_support/docs/
```

# 13. Doxygen Build Decisions

Documentation generation is controlled by:

```text
GAMEWIP_BUILD_DOCS
```

The root docs target combines:

* root project pages;
* project decisions;
* checklists;
* public header API reference;
* per-library Markdown guides.

Project-wide Doxygen helper functions live in:

```text
cmake/LibraryDoxygen.cmake
```

Each library registers its own public headers and docs folder when documentation is enabled.

Only the library landing page is required. Child pages are owned by the library landing page so navigation stays grouped.

Generated docs intentionally disable graph and PlantUML output for now so the docs target stays fast and deterministic.

When `GAMEWIP_BUILD_DOCS=ON`, Doxygen is required. If Doxygen is missing, configuration should fail with a clear message.

Normal builds must not require Doxygen.

`GAMEWIP_INSTALL_DOCS=ON` installs generated HTML docs under:

```text
share/doc/Libraries/doxygen/html
```

`GAMEWIP_INSTALL_DOCS=ON` requires `GAMEWIP_BUILD_DOCS=ON`.

# 14. Test Hook Policy

Test hooks are controlled by separate compile-time flags:

```text
LOGGER_ENABLE_TEST_HOOKS
ASSERT_ENABLE_TEST_HOOKS
TERMINAL_ENABLE_TEST_HOOKS
```

Test hooks live in internal headers such as:

```text
tools/logger/internal/logger_test_hooks.h
tools/debug/assert/internal/assert_test_hooks.h
foundation/terminal/internal/terminal_test_hooks.h
```

Callable test-hook APIs live under `GameWIP::<Library>::TestHooks`.

Internal hook state and hook machinery live under `GameWIP::<Library>::Detail::TestHooks`.

Hook namespaces only exist when the matching hook flag is enabled.

Hooks are not production API and should not be installed as public headers.

One-shot hooks use `forceNext...` naming.

Persistent hooks use:

```text
set...Override
clear...Override
```

Every hook must be resettable so tests cannot leak forced state into later tests.

# 15. Manual UI Test Policy

Manual UI tests are allowed to block because the user is intentionally validating real Windows UI.

They must be gated by runtime options.

Manual UI tests should run at the end of the suite.

Automated tests must not depend on clicking real dialogs.

# 16. Performance Policy

Hot paths should stay cheap.

Passing assert, check, verify, and ensure macros should remain extremely low overhead.

Filtered logger macros should avoid argument and message evaluation.

Normal logs should avoid unnecessary heap work on the producer path.

`Logger::report` is intentionally synchronous and may block. It is not the hot-path logging API.

Google Benchmark owns performance iteration, calibration, timing, repetition, and statistics.

Correctness tests do not contain benchmark loops or timing thresholds. CI builds and dry-runs benchmark registrations but does not fail changes based on machine-dependent timing values.

Asynchronous benchmarks must state whether they measure main-thread CPU, process CPU, or real elapsed time. Resource setup and teardown stay outside measured iterations.

# 17. Coverage Policy

Coverage answers which lines, functions, and branches actually ran during tests.

Coverage instrumentation is a compile-time build mode controlled by:

```text
GAMEWIP_ENABLE_COVERAGE
```

Runtime test selection still belongs to runtime options.

When coverage is enabled, the build should expose a `coverage` target.

If `gcovr` is available, the target generates:

* HTML report;
* XML report.

If `gcovr` is missing, the target fails with a clear installation message instead of silently disappearing.

Some GCC/gcov versions may produce negative hit counters for branch data. This is treated as a known gcov parse issue. The coverage target may pass:

```text
--gcov-ignore-parse-errors negative_hits.warn_once_per_file
```

Warnings should remain visible, but HTML and XML reports should still be generated.

# 18. Package and Install Naming

Package names match their library targets:

```cmake
find_package(IO CONFIG REQUIRED)
find_package(Terminal CONFIG REQUIRED)
find_package(FileSystem CONFIG REQUIRED)
find_package(Logger CONFIG REQUIRED)
find_package(Assert CONFIG REQUIRED)
find_package(TestSupport CONFIG REQUIRED)
```

Imported targets use the direct library names:

```cmake
IO
Terminal
FileSystem
Logger
Assert
TestSupport
```

The Terminal and FileSystem packages depend on the IO package.

The Logger package depends on the shared Terminal package. FileSystem and IO are private implementation dependencies embedded into the Logger shared library.

The Assert package depends on the Logger package.

The TestSupport package has no project-library dependencies.

Test hooks are excluded from public package installs by default.

# 19. CMake Standard

CMake is part of the library surface.

CMake should:

* use clear option names;
* avoid duplicated logic;
* keep project-wide options in the top-level CMake;
* keep library-specific options in each library CMake;
* avoid using CMake to control runtime test selection.

Standard C++ should be preferred:

```cmake
CMAKE_CXX_EXTENSIONS OFF
```

unless a toolchain dependency requires otherwise.

# 20. Commit Message Standard

Commit messages should read like compact public changelog entries.

The first line uses this format:

```text
area: imperative summary
```

Examples:

```text
filesystem: add Win32 platform backend
logger: split implementation into focused modules
tests: migrate logger and assert tests to test_support
```

The body uses patch-note style sections when they apply:

```text
Added:
- Added new APIs, modules, targets, tests, docs, or assets.

Changed:
- Changed existing behavior, structure, wiring, or documentation.

Fixed:
- Fixed bugs, incorrect behavior, edge cases, or broken workflows.

Removed:
- Removed obsolete files, docs, code paths, or temporary artifacts.

Build:
- Changed CMake, toolchain, package, install, editor, or dependency setup.

Tests:
- Added or changed test coverage, test support, validation, or checklists.

Documentation:
- Added or changed docs, examples, public API notes, or developer guidance.

Internal:
- Changed implementation details that matter to future maintainers.
```

Only include sections that actually apply to the commit.

Commit bodies should describe meaningful user-facing, maintainer-facing, or workflow-facing changes. They should not list every edited file unless the file itself explains an important decision.

Use past-tense section bullets for patch-note readability:

```text
Added:
- Added the filesystem target, package config, and API contract tests.
```

Avoid vague summaries:

```text
Updated stuff
Improved documentation
Initial header done
```

Prefer summaries that explain the real change:

```text
docs: add Doxygen documentation system
filesystem: add public filesystem library
assert: optimize assertion handling
```

Merge commits should be avoided on `master` for local amend/fixup workflows. If a pushed commit is amended, update the remote with a safe force push:

```text
git push --force-with-lease origin master
```

When pulling a rewritten branch, prefer rebasing over creating a merge commit:

```text
git pull --rebase origin master
```

The `master` history should remain a readable single line unless there is a deliberate reason to preserve a merge.

# 21. Repository Workflow Standard

Repository workflow standards live in:

```text
docs/contributing.md
```

The workflow standard covers:

* issue title and label conventions;
* branch naming;
* pull request descriptions;
* validation notes;
* merge style;
* squash commit messages;
* local sync after merge.

Normal feature work should use an issue, a focused branch, a pull request, and a squash merge into `master`.

Automated GitHub validation should stay easy to understand. The current standard is:

* pull request metadata standards run on ready-for-review pull requests into `master`;
* build/test validation runs on pull requests into `master`, pushes to `master`, and manual dispatch;
* documentation validation runs on pull requests into `master`, pushes to `master`, and manual dispatch;
* static analysis covers project-owned C++ under `foundation`, `tools`, `engine`, and `game`, while excluding external and generated code;
* JavaScript, JSON, and GitHub Actions workflows use format-appropriate repository checks;
* documentation publishing runs from `master` and manual dispatch;
* project automation derives deterministic status and linked-PR metadata from issue, pull request, and dependency state;
* a scheduled reconciliation repairs state changes that do not emit a usable repository event.

Dependabot pull requests may bypass human PR metadata checks, but they still run the normal validation workflow.

Branch protection should require the PR standards, build/test, repository, and documentation checks before merging into `master`.

Do not add noisy branch-wide automation beyond pull requests and `master` unless the project deliberately decides that the extra feedback is worth the extra GitHub Actions activity.

Project automation must preserve manual metadata, avoid comments, write a concise Actions summary, and support a dry run. A dedicated `PROJECT_TOKEN` secret owns project access; untrusted pull request code must never execute with that token.

# 22. Modular Validation Architecture

Correctness tests and benchmarks live under `game/validation` as discovered modules with explicit source and dependency lists.

The shared module object libraries are linked into:

* standalone `GameWIPTests` and `GameWIPBenchmarks` executables for CI and focused local work;
* `GameWIP` only when the corresponding startup-validation option is enabled.

`game/main.cpp` keeps a stable startup sequence: correctness tests, benchmark reporting, then the game runtime. Disabled startup validation resolves to inline successful/no-op functions and does not retain module or Google Benchmark dependencies.

Correctness-test failures stop game startup. Child-process test invocations return directly with their child exit code. Benchmark timing values are informational and do not gate startup.

The validation parent CMake files discover only immediate child directories containing `CMakeLists.txt`. Every module CMake file explicitly lists its sources and linked libraries so build-graph changes remain reviewable.

Test modules register a stable name, deterministic order, callback, and optional child-argument matcher. CTest invokes the standalone runner once per module with isolated report output.

Validation fixture files and subsystem test logs use `TestSupport::ScopedTemporaryDirectory`. Scoped workspaces live under the operating-system temporary directory and are removed after normal completion or exception unwinding. Relative validation report paths resolve beneath the GameWIP OS-temp root; absolute report paths are explicit user overrides. Only final reports persist by default, and validation does not create repository-relative `logs` directories.

Correctness validation writes complete detail to its report file and minimal failure/skip/manual information to stdout. The outer runner owns one result line per module and one aggregate result. `--verbose-tests` enables full console mirroring. Report-file failures emit diagnostics but do not alter correctness results.

Project build modes are defined through named CMake presets. Shipping builds disable standalone and startup validation, assertions, Tracy, and tools.

# 23. How to Add Future Decisions

When adding a decision:

1. Put it in the closest existing section.
2. Write the stable decision first.
3. Add rationale only if it prevents future confusion.
4. Do not add temporary tasks here.
5. Do not duplicate checklist items here.
6. Move large technical contracts into dedicated contract files.
7. Keep wording neutral and current.

A good decision entry explains what the project has decided and what future code should follow.

A bad decision entry only says what was implemented once.
