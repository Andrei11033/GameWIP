Library, tooling, and test standards
====================================

Purpose
-------
The logger, assert, and testing libraries are foundation code. They should be treated as small reusable libraries, not as throwaway game helpers. A feature is considered complete only when its public contract is documented, its normal and failure paths are tested, and its hot-path cost is understood.

Logger contract
---------------
- Normal log calls (`trace`, `debug`, `info`, `warn`, `error`, `fatal`) are asynchronous, queue-based, and filterable.
- `Logger::fatal(...)` is a normal fatal-severity log. It does not force a popup, synchronous flush, or process termination.
- `Logger::report(...)` is the synchronous diagnostic path. It bypasses level/source filters, bypasses the async queue, writes immediately to active sinks, mirrors to platform debug output when enabled, flushes sinks, and never terminates by itself.
- `Logger::report(timeout)` writes the report first, then performs a bounded queue/sink drain. A timeout failure does not mean the report line was lost.
- `reportError`, `reportFatal`, and `fatalTerminate` are convenience wrappers over the report path. `reportFatal` and `fatalTerminate` are allowed to use the logger-owned fatal popup when configured.
- Queue-drop counters only mean queue pressure. Filtered messages are intentional skips and must not count as drops.
- Unknown `SourceId` values are accepted, written with fallback source text, and counted through `unknownSourceUses`.

Assert contract
---------------
- `ASSERT`, `VERIFY`, and `UNREACHABLE` are fatal assertion paths when enabled.
- `CHECK`, `CHECK_ONCE`, and `ENSURE` are recoverable diagnostic paths.
- `ASSERT_INTERACTIVE` and `VERIFY_INTERACTIVE` are separate developer/debug features. They do not change the behavior of normal `ASSERT` or `VERIFY`.
- Interactive actions are `Break`, `Abort`, `IgnoreOnce`, and `AlwaysIgnore`. `AlwaysIgnore` is local to the macro call site.
- Automated interactive tests must use `GAMEWIP_ASSERT_TEST_ACTION` and must not open real popups.
- Manual UI tests are separate. They show real Windows UI, are allowed to block, and should run near the end of a test run.

TestSupport library contract
----------------------------
- `tools/test_support` is the shared GameWIP-native test support library for logger tests, assert tests, and future engine tests.
- The target is `TestSupport`, the alias is `GameWIP::TestSupport`, the public namespace is `GameWIP::TestSupport`, and the public header is `tools/test_support/test_support.h`.
- The library is a static library with generic test support only.
- `tools/test_support` must not depend on Logger or Assert. Logger and Assert tests may depend on TestSupport, but TestSupport must not know Logger or Assert concepts.
- TestSupport is not a replacement for GoogleTest. It is a small project-native support layer for reporting, expectations, child processes, manual checks, metrics, files, environment variables, and stress helpers.
- Runtime test behavior belongs in runtime options such as report options and suite options. CMake controls only compile-time and build features.
- The default report path is `logs/tests/latest_test_report.txt`. Report output should create parent directories as needed.
- Report output categories are `[INFO]`, `[PASS]`, `[FAIL]`, `[SKIP]`, `[MANUAL]`, `[METRIC]`, `[STRESS]`, `[SUMMARY]`, and `[RESULT]`.
- Expectations record failures and keep the runner alive. They must not call engine `ASSERT` / `CHECK` macros.
- Failures include `std::source_location`.
- Performance measurements are metrics-only for now. No hard pass/fail thresholds are part of the initial TestSupport contract.
- Windows environment helpers must update both the CRT environment used by `std::getenv()` and the process environment used for child process creation.
- Child process support should report exit code, timeout, test-requested termination, and captured output when enabled. Do not overpromise portable crash classification; nonzero exit and timeout are enough for GameWIP tests.
- Manual checks are opt-in runtime behavior and are used only when code cannot verify the result automatically.
- Concurrency helpers stay small: start gates, stop flags, and worker launching for stress tests only.

Planned TestSupport API
-----------------------
- `Types::ReportOptions` controls console output, report-file output, append behavior, and report path.
- `Types::Summary` tracks passed, failed, and skipped counts and exposes `total()` and `ok()`.
- `Types::SuiteResult` stores the suite name, summary, elapsed milliseconds, and `ok()`.
- `Context` is the main suite API. It writes info/manual/metric/stress/summary messages, records pass/fail/skip outcomes, exposes expectations such as `expectTrue`, `expectFalse`, `expectEq`, `expectNe`, `expectNear`, `expectContains`, `expectFileContains`, and `expectFileOccurrenceCount`, and exposes `suiteName()`, `result()`, and `ok()`.
- `Runner` owns one run-level report, runs named suites, reports run-level info/summary messages, exposes aggregate `result()`, and returns an `exitCode()`.
- `Section` is an RAII helper for grouping large test sections and may time/report section duration.
- `Timer` and `Types::IterationMetric` provide elapsed milliseconds and nanoseconds-per-iteration metrics.
- File helpers cover reading, writing, existence checks, substring checks, occurrence counts, directory creation, and best-effort removal.
- `ScopedEnvironmentVariable` and `ScopedUnsetEnvironmentVariable` restore environment state on destruction.
- `Types::ChildProcessOptions`, `Types::EnvironmentVariable`, `Types::ChildProcessResult`, and `runChildProcess()` cover child process tests.
- `Types::ManualAnswer` and `promptManualCheck()` cover explicitly enabled manual UI checks.
- `StartGate`, `StopFlag`, and `runWorkers()` cover basic stress-test coordination.

Runtime test control
--------------------
CMake builds the code. `TestRunOptions` controls which tests run and how intense they are. Stress tests, performance metrics, automated interactive tests, manual UI tests, logger popup tests, child crash tests, thread counts, iteration counts, and report output paths are runtime test options, not CMake test-selection options.

Naming standard
---------------
- Public C++ types use `PascalCase`.
- Public C++ functions use `camelCase`.
- Private/internal helpers use `camelCase`.
- Private/internal structs and classes use `PascalCase`.
- Constants use `kPascalCase`.
- Macros use `UPPER_SNAKE` and GameWIP-owned configuration macros use the `GAMEWIP_` prefix.
- CMake project-level options use `GAMEWIP_ENABLE_...`.
- CMake library-local options use `LOGGER_...`, `ASSERT_...`, or `TEST_SUPPORT_...`.
- Exported compiler macros use `GAMEWIP_LOGGER_...`, `GAMEWIP_ASSERT_...`, and `GAMEWIP_TEST_SUPPORT_...`.
- Names should describe the contract, not stale implementation history. For example, automated interactive tests are named separately from manual UI tests.
- Avoid global namespace pollution. Test hooks live under `GameWIP::LoggerDetail::TestHooks` and `GameWIP::Debug::Assert::TestHooks` only when enabled. Logger hooks use `LoggerDetail` because `GameWIP::Logger` is the public logger class, not a namespace.

Public API organization standard
--------------------------------
- Passive public data shapes live under `GameWIP::<Lib>::Types`.
- Passive data shapes include configs, options, results, summaries, enums, simple value structs, and wrapper values whose main purpose is to carry data across API calls.
- Active behavior stays directly under `GameWIP::<Lib>`.
- Active APIs include functions, runners, contexts, RAII guards, timers, synchronization helpers, services, and objects whose purpose is to perform work or manage lifetime.
- Do not add top-level aliases for `Types` members unless compatibility with already-shipped API requires it. Keeping passive data under `Types` makes IntelliSense and docs easier to scan.
- Current examples: Logger keeps `Types::Config`, `Types::Stats`, and `Types::Result` under `Types`; TestSupport keeps `Types::ReportOptions`, `Types::Summary`, and `Types::ChildProcessResult` under `Types`, while `Context`, `Runner`, `Timer`, `ScopedEnvironmentVariable`, and `runChildProcess()` remain directly under `GameWIP::TestSupport`.

Platform backend standard
-------------------------
GameWIP tool libraries keep public headers and `core/` implementations platform-neutral. OS-specific behavior lives behind internal platform headers and source files under `platform/<platform-id>/`.

`cmake/GameWIPPlatform.cmake` resolves `GAMEWIP_PLATFORM_ID`. Current Windows builds use `win32`. Library CMake files consume `platform/${GAMEWIP_PLATFORM_ID}/*.cpp` by convention and optionally include `platform/${GAMEWIP_PLATFORM_ID}/platform.cmake` for platform-only link libraries, resources, compile definitions, or generated files.

Adding a new platform should normally require adding the matching `platform/<platform-id>/` backend files and, when needed, that folder's `platform.cmake`. It should not require editing core implementation files or adding more platform-specific branches to the library root CMake files. Shared internal contracts and test hooks should use backend-neutral names unless the hook is intentionally scoped to one backend.

Windows Unicode backend standard
--------------------------------
Windows platform code uses explicit Unicode Win32 APIs. Public GameWIP C++ APIs stay portable and ergonomic by using `std::string` for UTF-8 text and `std::filesystem::path` for paths. At the Win32 boundary, platform backends convert to UTF-16 and call explicit `W` APIs such as `CreateProcessW`, `MessageBoxW`, `GetEnvironmentStringsW`, `SetEnvironmentVariableW`, and `OutputDebugStringW`.

Do not use ANSI Win32 APIs such as `CreateProcessA`, `MessageBoxA`, `GetEnvironmentStringsA`, or `OutputDebugStringA` in new platform code. Also avoid generic macro-mapped APIs such as `CreateProcess`, `MessageBox`, `GetEnvironmentStrings`, and `OutputDebugString`, because their behavior depends on the `UNICODE` build definition and can silently change between `A` and `W` variants.

The standard for Windows backends is:
- public API: UTF-8 `std::string` / portable `std::filesystem::path`;
- platform boundary: explicit UTF-8 to UTF-16 conversion where needed;
- Win32 calls: explicit `W` functions;
- captured process output: byte-oriented `std::string`, because stdout/stderr pipes carry bytes.

This applies to Logger, Assert, TestSupport, and future Windows backends.

Documentation / IntelliSense standard
--------------------------------------
Public API comments use professional Doxygen-style documentation focused on contracts. Public headers should explain behavior, lifecycle expectations, thread-safety where relevant, failure behavior, blocking/UI behavior, and performance notes. Full tutorials, complete usage explanations, examples, and edge-case discussions belong in generated Doxygen Markdown manual pages, not in hover-heavy header comments.

Public headers should follow the Logger/Assert style:
- Start with `/// @file` and `/// @brief` when the header is a public entry point.
- Use `/// @brief` on public namespaces, types, enum values, fields, functions, macros, and important templates.
- Use `@param`, `@return`, and `@note` where they improve IntelliSense or generated docs.
- Prefer IntelliSense-friendly plain sections such as `Contract:`, `Thread-safety:`, `Failure behavior:`, `Blocking behavior:`, and `Performance:` in public headers. Use custom Doxygen aliases only where they improve the generated pages without making editor hovers noisy.
- Keep the first line short and useful in IntelliSense. Put detailed workflows, examples, and conceptual explanations in the library Markdown pages.
- Public header docs should be complete enough for on-the-spot coding: parameters, return values, the main contract, and important warnings must be visible in IntelliSense.
- Header comments should stay compact: no long tutorials, no large examples, and no full design manuals in hover text. If a comment starts to explain a workflow, move that explanation to the library Markdown manual and leave a short reference in the header.
- The generated Doxygen manual must cover every public API. Simple APIs may be fully covered by the header reference; non-trivial APIs must also be covered by a Markdown guide page with usage rules, edge cases, performance notes, and examples.
- Macro APIs use `@def` blocks, as Assert does, so generated docs and hover text show macro behavior clearly.
- Implementation helpers use `@cond` / `@endcond` when they must appear in a public header but should not be treated as normal API.

Internal code should be documented when it protects a non-obvious invariant: locking, atomics, shutdown/lifecycle rules, platform assumptions, hot paths, failure injection, or test hooks. Do not add comment noise for obvious syntax.

Test hook policy
----------------
- Test hooks use separate compile-time flags: `GAMEWIP_LOGGER_TEST_HOOKS` and `GAMEWIP_ASSERT_TEST_HOOKS`.
- Test hooks live in internal headers: `tools/logger/internal/logger_test_hooks.h` and `tools/debug/assert/internal/assert_test_hooks.h`.
- Hook namespaces only exist when the matching hook flag is enabled.
- Hooks are not production API and should not be installed as public headers.
- One-shot hooks use `forceNext...` naming.
- Persistent hooks use `set...Override` / `clear...Override` naming.
- Each hook must be resettable so tests cannot leak forced state into later tests.

Coverage policy
---------------
Coverage answers which lines, functions, and branches actually ran during tests. Coverage instrumentation is a compile-time build mode and therefore belongs in CMake (`GAMEWIP_ENABLE_COVERAGE`). Runtime test selection still belongs to `TestRunOptions`. Coverage is especially useful after test hooks exist, because hooks make rare fallback and failure branches reachable.

Manual UI test policy
---------------------
Manual UI tests are allowed to block because the user is intentionally validating real Windows UI. They must be gated by runtime options and should run at the end of the suite. Automated tests must not depend on clicking dialogs.

Performance policy
------------------
Hot paths should stay cheap. Passing assert/check/verify/ensure macros should remain extremely low overhead. Filtered logger macros should avoid argument/message evaluation. Normal logs should avoid unnecessary heap work on the producer path. `Logger::report` is intentionally synchronous and may block; it is not the hot-path logging API. Performance tests are metrics-only for now: they report regressions but do not fail the run based on hard thresholds.

Package/install naming policy
-----------------------------
Package/install polish uses package names with an underscore:
- `find_package(GameWIP_Logger CONFIG REQUIRED)`
- `find_package(GameWIP_Assert CONFIG REQUIRED)`
- `find_package(GameWIP_TestSupport CONFIG REQUIRED)`

Targets stay namespaced and stable:
- `GameWIP::Logger`
- `GameWIP::Assert`
- `GameWIP::TestSupport`

The Assert package depends on the Logger package. TestSupport has no Logger or Assert dependency. Test hooks are excluded from public package installs by default.

CMake standard
--------------
CMake should be treated as part of the library surface. It should use clear option names, avoid duplicated logic, keep project-wide options in the top-level CMake, keep library-specific options in each library CMake, and avoid using CMake to control runtime test selection. Standard C++ should be preferred (`CMAKE_CXX_EXTENSIONS OFF`) unless a toolchain dependency requires otherwise.

Generated documentation and package polish
------------------------------------------
Doxygen generation is provided by the optional `GAMEWIP_BUILD_DOCS` CMake option and the `docs` target. The first Doxygen setup documents the logger/assert public surface and uses custom aliases for contract-oriented sections such as thread-safety, lifecycle, performance, and test-only notes.

Install/package polish uses underscore package names (`GameWIP_Logger`, `GameWIP_Assert`, and `GameWIP_TestSupport`) while keeping imported targets stable as `GameWIP::Logger`, `GameWIP::Assert`, and `GameWIP::TestSupport`. The Assert package locates the Logger package as a dependency and propagates the Common Controls v6 manifest resource through `GameWIP::Assert` for Windows consumers. The TestSupport package has no Logger or Assert package dependency.

Per-library documentation structure
-----------------------------------
Each reusable library may own a `docs/` directory next to its public headers. These pages are written as Doxygen-compatible Markdown and are intended to answer practical usage questions without requiring the reader to inspect implementation files.

The root documentation target combines:
- root project pages such as `docs/doxygen/index.md`, decisions, and checklists;
- public header API reference generated from Doxygen comments;
- per-library Markdown guides such as `tools/logger/docs/`, `tools/debug/assert/docs/`, and `tools/test_support/docs/`.

The intended split is:
- public header comments document API contracts, parameters, return values, lifecycle behavior, thread-safety, failure behavior, blocking behavior, and performance notes for IntelliSense and the generated API reference;
- per-library Markdown pages document quick starts, public API guides, concepts, examples, edge cases, troubleshooting, and common usage patterns;
- developer-validation pages such as testing and test-hook notes may exist, but they are separate from the normal user manual and must not present test-only APIs as production APIs;
- root docs explain project-level build, testing, coverage, and documentation workflows.

The global `GAMEWIP_BUILD_DOCS` option controls whether documentation is built. Each library CMake file registers its public headers and `docs/` directory only when the global documentation option is enabled and the root project provides the registration helper. This keeps library docs modular while still producing one combined `docs` target for the whole project.

Coverage and documentation tool behavior
----------------------------------------
When `GAMEWIP_ENABLE_COVERAGE` is enabled, the build should always expose a `coverage` target. If `gcovr` is available, the target generates HTML and XML reports. If `gcovr` is missing, the target fails with a clear message explaining how to install it. This avoids silent missing-target confusion.

When `GAMEWIP_BUILD_DOCS` is enabled, Doxygen is required. If Doxygen is missing, configuration should fail with a clear message. Normal builds must not require Doxygen.

Doxygen architecture update
---------------------------
- Project-wide Doxygen helper functions live in `cmake/GameWIPDoxygen.cmake`.
- Each library owns its own docs folder and registers its public headers plus docs folder from its own `CMakeLists.txt`.
- Only the library landing page (`<lib>.md`) is required. Other pages are library-defined.
- Root docs should link only major sections. Each library landing page owns its child `@subpage` links so the sidebar stays grouped by library.
- `GAMEWIP_INSTALL_DOCS=ON` installs generated HTML docs under `share/doc/GameWIP/doxygen/html` and requires `GAMEWIP_BUILD_DOCS=ON`.
- The Doxygen input list is generated as one physical line to avoid fragile backslash parsing on Windows/MSYS2 paths.
- Generated docs intentionally disable graph/PlantUML output for now so the `docs` target stays fast and deterministic.

Coverage gcov/gcovr note
------------------------
Some GCC/gcov versions can produce negative hit counters for branch data. The coverage target treats this as a known gcov parse issue and passes `--gcov-ignore-parse-errors negative_hits.warn_once_per_file` to gcovr so HTML/XML reports are still generated while warnings remain visible.
