# GameWIP Testing Checklist

## Purpose

This file defines what must be proven by tests, manual validation, metrics, or documentation inspection.

It answers:

> “Has this behavior been validated?”

This file intentionally focuses on observable contracts and failure coverage, not implementation history.

* Use `implementation_checklist.txt` for what has been implemented.
* Use `roadmap.txt` for planned development order.
* Use `decisions.txt` for stable project decisions and standards.
* Use `platform_backend_contract.txt` for backend boundary rules.

---

## Status Legend

```text
[ ] Not validated
[-] Validation in progress
[x] Validated
[~] Partially validated / needs follow-up
[!] Blocked or waiting on a decision
[M] Manual validation required
```

# 12. How to Extend This File

When adding validation requirements:

1. Add the item under the closest existing system section.
2. Use `[ ]` for behavior that has not been validated.
3. Use `[-]` for validation currently in progress.
4. Use `[~]` for partial validation.
5. Use `[x]` only when the behavior has actually been tested, manually checked, measured, or inspected.
6. Use `[M]` when real manual validation is required.
7. Do not mark something validated because it is implemented.
8. Do not add implementation tasks here; put them in `implementation_checklist.txt`.
9. Do not add roadmap planning here; put it in `roadmap.txt`.
10. Do not add architecture decisions here; put them in `decisions.txt`.
11. Prefer observable behavior over implementation details.
12. Include failure paths and edge cases when they are part of the public contract.

A good testing checklist item says what behavior must be proven.

A bad testing checklist item only says what code exists.
