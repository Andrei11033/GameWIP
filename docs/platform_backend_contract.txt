# Platform Backend Contract

## Purpose

The libraries keep public APIs and core implementation code platform-neutral.

Platform-specific behavior lives behind small internal backend contracts selected by the build system through `LIBRARY_PLATFORM_ID`.

This file defines the project-wide convention for platform backend layout, build selection, and backend responsibilities.

---

# 1. Core Rule

Core code must not call operating-system APIs directly.

This applies to reusable libraries such as:

* IO;
* Terminal;
* FileSystem;
* Logger;
* Assert;
* TestSupport;
* future engine libraries that need platform-specific behavior.

Core code should depend on internal platform-neutral declarations. Platform-specific source files implement those declarations for each supported platform.

The goal is to make platform support additive.

Adding a new platform should normally require adding a new backend folder, not rewriting core logic.

---

# 2. Platform Selection

`LIBRARY_PLATFORM_ID` is the build-system platform key.

Current Windows builds resolve it to:

```text
win32
```

The platform id is resolved by:

```text
cmake/LibraryPlatform.cmake
```

Library CMake files should consume platform-specific files using this convention:

```text
platform/${LIBRARY_PLATFORM_ID}/*.cpp
```

A library may also include a platform-specific CMake file when needed:

```text
platform/${LIBRARY_PLATFORM_ID}/platform.cmake
```

Use `platform.cmake` only for backend-local target requirements, such as:

* system libraries;
* compile definitions;
* resources;
* manifests;
* generated source files.

---

# 3. Backend Folder Layout

Each library that needs platform-specific behavior may provide backend files under:

```text
foundation/<library>/platform/<platform-id>/
tools/<library>/platform/<platform-id>/
```

Backend source files follow this naming convention:

```text
platform/<platform-id>/<platform-id>_<feature>.cpp
```

Examples:

```text
foundation/terminal/platform/win32/win32_terminal.cpp
foundation/filesystem/platform/win32/win32_filesystem.cpp
tools/logger/platform/win32/win32_logger.cpp
tools/test_support/platform/win32/win32_environment.cpp
tools/test_support/platform/win32/win32_child_process.cpp
```

The backend folder may optionally contain:

```text
platform/<platform-id>/platform.cmake
```

---

# 4. Adding a New Platform

To add a new platform:

1. Add or update platform id detection in `cmake/LibraryPlatform.cmake`.
2. Add matching backend folders where platform-specific behavior is required.
3. Implement the required internal backend contracts.
4. Add `platform.cmake` files only when the backend has target-local build requirements.
5. Avoid adding platform branches to core implementation files.
6. Avoid adding platform-specific behavior to public headers unless it is part of the public contract.

A good new platform port adds files.

A bad new platform port spreads `#ifdef` logic through core code.

---

# 5. Public API Boundary

Public library APIs should stay portable and ergonomic.

Preferred public API types:

* `std::string` for UTF-8 text;
* `std::filesystem::path` for paths;
* ordinary C++ value types for configuration and results.

Platform backends are responsible for converting these portable types into platform-specific representations when needed.

For Windows, this means converting UTF-8 text to UTF-16 at the Win32 boundary and calling explicit Unicode APIs.

---

# 6. Internal Backend Namespace Layout

Platform backend declarations and definitions live under the owning library namespace.

Use:

```cpp
GameWIP::<Library>::Detail::Platform
```

for platform backend declarations/definitions.

Use:

```cpp
GameWIP::<Library>::Detail::Core
```

for platform-neutral internal implementation helpers.

Use:

```cpp
GameWIP::<Library>::TestHooks
GameWIP::<Library>::Detail::TestHooks
```

for callable test-only hooks and private hook machinery respectively.

Do not introduce sibling detail namespaces such as `GameWIP::LoggerDetail` or `GameWIP::TerminalDetail` for new or refactored code.

---

# 7. IO Core Boundary

IO is intentionally platform-neutral and has no backend folder.

It defines byte-transfer interfaces, portable status/error shapes, memory-backed readers and writers, and whole-stream helpers used by resource-owning libraries. IO must not open files, access terminal handles, or call operating-system APIs.

Foundation libraries may depend on IO status and transfer contracts. IO must not depend on Terminal, FileSystem, Logger, Assert, TestSupport, engine code, or game code.

---

# 8. Terminal Backend Contract

Terminal core owns public option validation, formatting, style/control sequence assembly, per-stream serialization, and scoped state nesting. It delegates standard-handle capabilities, Unicode conversion, input waiting/reading, input-mode snapshots, raw writes, and native flushing through:

```text
foundation/terminal/internal/terminal_platform.h
```

## Required Responsibilities

A Terminal backend is responsible for:

* classifying stdin, stdout, and stderr as terminal, redirected, detached, or other;
* observing and preparing terminal capabilities without inventing unsupported features;
* converting public UTF-8 text at a native text boundary;
* preserving redirected output as bytes;
* retaining incomplete UTF-8/input fragments across reads;
* providing timeout-aware input without unbounded waits;
* capturing and exactly restoring native input mode state;
* reporting terminal size and cursor position only when reliable;
* validating backend limits for cursor, scroll, and title operations.

Terminal test hooks may replace capabilities, input bytes, input mode, query results, and output capture. Hook state is process-wide and must be reset between scenarios.

---

# 9. FileSystem Backend Contract

FileSystem core owns public option validation, handle object semantics, whole-file orchestration, atomic-write lifecycle, recursive traversal policy, and portable status mapping. Native path traversal, handles, metadata, sharing, locks, and mutation are declared in:

```text
foundation/filesystem/internal/filesystem_platform.h
```

## Required Responsibilities

A FileSystem backend is responsible for:

* opening read, write, and read/write handles with exact access, sharing, and creation semantics;
* preserving accepted read/write progress on later failure;
* querying portable metadata through stable native handles;
* implementing non-blocking whole-file locks and explicit unlock failure;
* creating, listing, moving, copying, and removing entries without check-then-use races where the contract forbids them;
* preserving portable timestamps and read-only metadata where requested;
* flushing file and directory metadata for durable atomic replacement;
* converting path text only at the native platform boundary.

`SymlinkPolicy::DoNotFollow` and `FollowFinal` are security contracts. The backend must reject forbidden intermediate name-surrogate entries during handle-relative traversal and keep traversal handles alive across multi-step operations. A backend that cannot enforce the requested policy safely must return `Unsupported`; it must not emulate safety with a metadata check followed by an unrelated path reopen.

File and lock state destructors perform best-effort native cleanup. Public `close()` and `unlock()` remain the paths that can report cleanup failure.

---

# 10. Logger Backend Contract

Logger core code must not call operating-system APIs directly.

The Logger backend implements the functions declared in:

```text
tools/logger/internal/logger_platform.h
```

## Required Responsibilities

A Logger backend is responsible for:

* writing text to the platform debugger or diagnostic stream;
* showing a fatal diagnostic popup when enabled by Logger configuration;
* creating directories for log files;
* opening log files;
* writing to log files;
* flushing log files;
* closing log files;
* reporting whether a file handle is open;
* formatting local time text used by log file names and log lines;
* reporting whether stdout or stderr supports ANSI color;
* returning best-effort process memory diagnostics;
* providing per-thread formatting scratch storage for header-only formatted logging paths.

## Producer-Side Logging Rule

Filtered `LOGGER_*` macro calls should check `shouldLog()` before evaluating message or format arguments.

Direct formatted Logger calls cannot prevent normal C++ argument evaluation before the call.

For expensive arguments, use one of these patterns:

```cpp
LOGGER_INFO(source, "value {}", expensiveValue());
```

or:

```cpp
if (Logger::shouldLog(...)) {
    Logger::info(...);
}
```

The macro path is preferred when argument evaluation should be avoided for filtered logs.

---

# 11. Assert Backend Contract

Assert core code must not call operating-system APIs directly.

The Assert backend implements the functions declared in:

```text
tools/debug/assert/internal/assert_platform.h
```

## Required Responsibilities

An Assert backend is responsible for:

* showing a non-interactive assertion or error popup when configured;
* showing an interactive assertion dialog;
* returning the selected interactive action;
* reporting whether a debugger is currently attached;
* triggering the platform debug-break instruction or trap.

## Passing-Path Rule

Assert passing paths should stay allocation-free and branch-light.

Macro documentation must clearly explain which condition and message expressions are evaluated in:

* enabled builds;
* disabled builds;
* diagnostics-enabled builds;
* diagnostics-disabled builds;
* fatal assertion paths;
* recoverable check paths;
* interactive assertion paths.

---

# 12. TestSupport Backend Contract

TestSupport core code must not call operating-system APIs directly.

The TestSupport backend implements the functions declared in:

```text
tools/test_support/internal/test_support_platform.h
```

Platform-specific child-process helpers used by the public TestSupport API are also implemented by the backend.

## Required Responsibilities

A TestSupport backend is responsible for:

* reading process environment variables;
* setting process environment variables;
* unsetting process environment variables;
* running child processes;
* passing arguments to child processes;
* applying child-process environment overrides;
* collecting child-process exit codes;
* collecting stdout and stderr when capture is enabled;
* reporting launch failures;
* reporting output read failures;
* reporting timeouts;
* reporting test-requested termination.

On Windows, a child process tree must be attached to kill-on-close job ownership so timeout cleanup also terminates descendants that inherited capture handles.

## Environment Rule

Environment helpers must update all environment views required by the platform.

For Windows, scoped environment helpers must update both:

* the CRT environment used by `std::getenv()`;
* the process environment used for child process creation.

## Child-Process Rule

Child-process support should report observable results.

It should not overpromise portable crash classification.

For the project tests, these are enough:

* zero exit;
* nonzero exit;
* timeout;
* test-requested termination;
* captured output when enabled.

---

# 13. Windows Backend Rules

Windows backends use explicit Unicode Win32 APIs.

Do not use ANSI APIs such as:

```cpp
CreateProcessA
MessageBoxA
GetEnvironmentStringsA
SetEnvironmentVariableA
OutputDebugStringA
```

Do not use generic macro-mapped APIs such as:

```cpp
CreateProcess
MessageBox
GetEnvironmentStrings
SetEnvironmentVariable
OutputDebugString
```

Generic Win32 API names depend on the `UNICODE` build definition and can silently change between ANSI and Unicode behavior.

Use explicit Unicode APIs such as:

```cpp
CreateProcessW
MessageBoxW
GetEnvironmentStringsW
SetEnvironmentVariableW
OutputDebugStringW
```

Windows backend rules:

* public API text remains UTF-8 `std::string`;
* public API paths remain portable `std::filesystem::path`;
* platform boundary code converts to UTF-16 where needed;
* Win32 calls use explicit `W` functions;
* captured process output remains byte-oriented `std::string`.

Captured stdout and stderr should remain bytes because process pipes carry bytes, not C++ text objects.

---

# 14. Backend-Neutral Test Hooks

Shared internal contracts and test hooks should use backend-neutral names unless the hook is intentionally scoped to one backend.

Good names:

```text
forceNextFileOpenFailure
forceNextPopupFailure
setDebuggerAttachedOverride
clearDebuggerAttachedOverride
```

Avoid names that expose the current platform unless the hook is truly platform-specific.

Backend-neutral hooks make it easier to reuse the same test expectations across future platforms.

---

# 15. Documentation Requirements

Every backend contract should be documented at the internal declaration point.

Internal platform headers should explain:

* what the backend function does;
* who owns memory or handles;
* what happens on failure;
* whether the function may block;
* whether the function is thread-safe;
* whether the function is used on hot paths;
* whether the function is test-hookable.

Backend implementation files should document non-obvious platform behavior, especially:

* Unicode conversion;
* handle ownership;
* process creation;
* environment synchronization;
* popup/dialog behavior;
* debug-break behavior;
* fallback paths;
* failure injection.

Do not add comments for obvious syntax.

Document invariants and platform assumptions.

---

# 16. Checklist for New Backend Work

Before backend work is considered complete:

* [ ] Core code does not call operating-system APIs directly.
* [ ] Backend files live under the correct `platform/<platform-id>/` folder.
* [ ] Source files follow the `<platform-id>_<feature>.cpp` naming convention.
* [ ] `platform.cmake` is used only for backend-local target requirements.
* [ ] Public APIs remain platform-neutral.
* [ ] Unicode/text/path behavior is documented.
* [ ] Failure behavior is documented.
* [ ] Blocking behavior is documented.
* [ ] Hot-path behavior is understood.
* [ ] Tests or test hooks cover important backend behavior where practical.
* [ ] Adding the backend did not require spreading platform branches through core code.

---

# 17. How to Extend This File

When adding to this contract:

1. Keep the file focused on platform boundaries.
2. Put library-specific backend responsibilities under that library section.
3. Put detailed implementation tasks in `implementation_checklist.txt`.
4. Put validation requirements in `testing_checklist.txt`.
5. Put long-term architecture decisions in `decisions.txt`.
6. Avoid documenting temporary implementation history.
7. Prefer rules that help future platforms stay easy to add.

A good backend contract says what every platform must provide.

A bad backend contract describes only how the current Windows implementation happens to work.
